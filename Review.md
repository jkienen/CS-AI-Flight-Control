# CrowdStrike AI Flight Control — Review

This file is the skill for reviewing and correcting the CrowdStrike Falcon CID (tenant) hierarchy. It covers the whole loop: load the current export, show the structure, collect the user's corrections, and produce the step-by-step text that CrowdStrike support uses to apply them.

Everything written to `Output/` (HTML, CSV, case text) is in English. Talk to the user in their language.

## Rules

These apply to every correction. They are set at the top of the generator (`Part 1: Setup`), so each organization can match its own conventions; read their current values there before the first correction. The generator enforces them, but catch them yourself first, before editing anything.

1. **CID names have at most `MAX_NAME` characters** (38 by default; `0` turns the rule off). When the user asks for a new name (rename or new CID) over the limit, stop: say how long it is, do not apply it, and suggest one or two shorter versions that keep the naming pattern the export already uses (for example, a service-line tag before `|`) and the recognizable part of the client's name, such as dropping a legal suffix or abbreviating a long word. Apply only the name the user confirms. Existing names over the limit are reported as warnings; point them out and offer a shorter name, but rename only if the user wants.
2. **With `INCIDENT_FOLLOWS_DETECTION` on (the default), Incident Aggregation always equals Detection Aggregation.** When a correction changes one of them on a CID, change the other the same way, and tell the user you did. If the export shows a CID where they differ, point it out and include the fix in the expected structure. With it off, the two settings are independent.

## Directory layout

```
Review.md                                 this file (the skill)
CLAUDE.md                                 Claude Code instructions: points every session here
Input/CIDs.csv                            CID export from the CrowdStrike Falcon console (provided by the user)
Input/CIDs_example.csv                    fictional sample export shipped with the repository
Output/Example/                           fictional sample review (expected structure, graph, case text) of that export
Output/Scripts/Generate-FlightControl.py  the generator: reads the CSVs, writes CIDs.html and Case_Message.txt
Output/<day>/                             one folder per day, named YYYY-MM-DD (for example Output/2026-10-14/):
  CIDs_Expected.csv                       the expected (target) structure; the source of truth for corrections
  CIDs.html                               interactive page of the structure (graph and table): Expected and Today views
  Case_Message.txt                        step-by-step text for CrowdStrike support, from Today to Expected
```

`Input/CIDs_example.csv` and `Output/Example/` are fictional samples. Never treat them as the user's export or expected structure, and never change them, unless the user asks to try the example; the generator ignores them (`Example/` is not a day folder).

Every run writes to today's folder, `Output/<day>/` below. Running again on the same day updates that folder; folders of earlier days are never changed and stay as the history of each review.

`CIDs.html` and `Case_Message.txt` are generated by [`Output/Scripts/Generate-FlightControl.py`](Output/Scripts/Generate-FlightControl.py). Never edit them by hand: change `CIDs_Expected.csv` and run the script again.

### Running the generator script

1. Run it from any folder (it finds `Input/` and `Output/` from its own location):

   ```
   python -I Output/Scripts/Generate-FlightControl.py                    # normal run
   python -I Output/Scripts/Generate-FlightControl.py --init-expected    # first correction: create today's CIDs_Expected.csv from the export
   python -I Output/Scripts/Generate-FlightControl.py --keep-expected    # go on from an earlier day: copy its most recent CIDs_Expected.csv into today's folder
   ```

2. Read its output:
   - `ERROR` means the input is unusable (wrong header, invalid or duplicate CIDs, a broken `CIDs_Expected.csv`). Nothing is written. Show the errors to the user and fix the cause.
   - `WARNING` lines do not block, but list every one to the user. They point to things like a `Parent` or `Additional Parent` that is not in the export, a CID that is not `active`, more than one root, `Is Parent?` not matching the CID's actual children, a CID below a tenant (deeper than root → service line → tenant), a name over `MAX_NAME` characters, Incident Aggregation differing from Detection Aggregation (with `INCIDENT_FOLLOWS_DETECTION` on), or a `NEW-<n>` CID that now exists in the export.
   - `OK` lines say what was written.
   - A `NOTE` says that today's folder has no `CIDs_Expected.csv` yet while an earlier day has one (see 0.2).

The script creates today's folder if it does not exist. It uses only the Python standard library, so there is nothing to install, and the HTML it writes is self-contained: it loads nothing from the internet, so it also opens offline.

The script does not change with the data: every correction goes into `Output/<day>/CIDs_Expected.csv`. Change the script only to change how the HTML or the case text looks or behaves, keep its code organization (the `Part N` sections, 2-space indentation), and update [What the HTML shows](#what-the-html-shows) or [What the case message contains](#what-the-case-message-contains) to match.

## 0. Session start (required every session)

Every new session starts with these steps, in order. Do not move on to anything else until they are done.

### 0.1 Confirm the CID export

1. Check that `Input/CIDs.csv` exists at the root of this directory.
2. **If it does not exist:** ask the user to download an up-to-date CID export from the CrowdStrike Falcon console and save it as `Input/CIDs.csv`.
3. **If it already exists:** do not assume it is current. Show the user the file's last-modified date and ask whether they want to replace it with a fresh export. Default to asking for a fresh export.
4. Continue only after the user confirms that `Input/CIDs.csv` is the current export.

The file is the CSV exported from the Falcon CID list, encoded in UTF-8, with this header:

```
CID Name,CID String,Customer ID Checksum (CCID),Status,Is Parent?,Parent,Additional Parent,CID Groups,Number of Endpoints,Number of Endpoints Seen Last 45 Days,Number of Child CIDs,Number of Total Endpoints,Number of Total Endpoints Seen Last 45 Days,Policy Inheritance,Detection Aggregation,Incident Aggregation,Domain Allowlist,Falcon Module Subscriptions,Application and Plugin Integrations
```

If the header is different, tell the user before continuing. It may be the wrong export, or CrowdStrike may have changed the format.

### 0.2 Check for an expected structure from a previous session

Look for the most recent `CIDs_Expected.csv`: in today's folder first, otherwise in the latest earlier `Output/<day>/` (the script prints a `NOTE` when only an earlier one exists). If there is one, ask the user which one they want:

- **Keep it:** the new export is compared against it. Use this to check what CrowdStrike support has already applied and what is still pending. When it is from an earlier day, run the script with `--keep-expected` to copy it into today's folder; the earlier folder stays as it was. If support created a CID that the expected structure lists as `NEW-<n>`, the script warns that it now exists in the export: replace `NEW-<n>` with its real CID String in today's `CIDs_Expected.csv` (also where other rows use it as a parent) and run the script again.
- **Start fresh:** when it is from an earlier day, do nothing: today's folder starts without one. When it is in today's folder, delete today's `CIDs_Expected.csv` and `Case_Message.txt`. Never delete earlier days' folders. The session starts again from the current structure only.

### 0.3 Render the structure

1. Run the generator script (normal run).
2. Tell the user where the file is (`Output/<day>/CIDs.html`) and summarize it: total CIDs, and how many tenants sit under each service-line parent. If an expected structure was kept in 0.2, also say what is still pending, or that everything matches.
3. Ask the user to open the HTML and tell you the corrections they want.

## 1. Corrections

The user reviews `Output/<day>/CIDs.html` and describes corrections in their own words. Turn each one into concrete changes, update the expected structure, and regenerate. Repeat until the user is satisfied. Corrections add up across rounds: each round edits the same `Output/<day>/CIDs_Expected.csv`.

### 1.1 Understand each correction

- Map every correction to specific CIDs, identified by CID String. Users refer to tenants by partial names; if a name could match more than one CID, ask.
- Before editing, repeat back what you understood as a short list of concrete changes (CID, field, current value, new value). Skip this only when the correction is trivially clear, such as a single rename or toggle.
- The script handles these changes:

| Change | How to express it in `CIDs_Expected.csv` |
|---|---|
| Rename a CID | Change `CID Name` (`MAX_NAME` characters at most) |
| Move a CID to another parent | Change `Parent CID` |
| Add or remove an additional parent | Set or clear `Additional Parent CID` |
| Enable or disable Policy Inheritance | Set the column to `true` or `false` |
| Enable or disable Detection Aggregation | Set `Detection Aggregation`, and `Incident Aggregation` to the same value while `INCIDENT_FOLLOWS_DETECTION` is on |
| Delete a CID | Remove its row (re-parent or remove its children first) |
| Create a new child CID | Add a row with `CID String` = `NEW-1`, `NEW-2`, ... |

If a correction does not fit this table (for example, combining tenants under a single login, user access, or module subscriptions), say so. Agree with the user how to word it, and add it to `Output/<day>/Case_Message.txt` by hand after the last generation, in its own section after the generated steps. Regenerating overwrites the file, so add it again after every run.

### 1.2 Update the expected structure

1. If today's `CIDs_Expected.csv` does not exist, create it with `--init-expected` (or with `--keep-expected`, when the user chose in 0.2 to go on from an earlier day). It starts as a copy of the current structure, so nothing is pending. With `INCIDENT_FOLLOWS_DETECTION` on, if the export has CIDs where Incident Aggregation differs from Detection Aggregation, that same run stops with an `ERROR` for each of them (the expected structure must follow the rule): ask the user which value to keep, set both columns to it, and run again.
2. Edit `Output/<day>/CIDs_Expected.csv`. Use Python's `csv` module (or careful edits that keep the quoting intact), and keep it UTF-8.

Format of `CIDs_Expected.csv`:

```
CID String,CID Name,Parent CID,Additional Parent CID,Policy Inheritance,Detection Aggregation,Incident Aggregation
```

- One row per CID that must exist in the expected structure.
- `Parent CID` and `Additional Parent CID` hold **CID Strings**, not names, so renames never break parent links. Leave `Parent CID` empty only for the root.
- Flags are `true` or `false`.
- New CIDs use `NEW-<n>` as their CID String. Other rows can reference them as a parent.
- The script refuses (`ERROR`) duplicate CIDs or names, CIDs that are not in the export, parents that are not in the file, parent cycles, new or changed names over `MAX_NAME` characters (unless it is `0`), and, with `INCIDENT_FOLLOWS_DETECTION` on, rows where Incident Aggregation differs from Detection Aggregation.

### 1.3 Regenerate and report

1. Run the generator script (normal run). It rewrites `Output/<day>/CIDs.html` and `Output/<day>/Case_Message.txt`.
2. Tell the user what changed in this round and what the full pending list is now (the script prints the counts).
3. Ask for the next round of corrections, or whether the case text is ready to send.

### What the HTML shows

`Output/<day>/CIDs.html` is one self-contained page laid out like the CID overview of the Falcon console: dark by default, with a light theme. The script writes the data into the page and the page draws everything itself (an SVG with its own pan and zoom), so it needs no library and no internet connection.

The page reads three parts of the naming pattern from the CID names, and works without them: the **number**, the text before ` - ` (`01` in `01 - Example Corp | Managed`), shown with each service line (lines are sorted by name, so a leading number also sets their order); the **short name**, the text after the last `|` (`Managed`), shown for the root and the service lines; and the **tag**, up to 6 characters before ` | ` at the start of a tenant's name (`MGD` in `MGD | Bravo Retail`), drawn in gray.

- **Header:** the page name and the company (from the root's name: the text between its number and the `|`, such as `Example Corp` in `0 - Example Corp | Global Parent`), a **Search** box (CID name or CID String; `/` focuses it, Enter jumps to the first match, Esc clears it), the view switch and the light/dark button (the browser remembers the choice).
  - **View:** **Expected** ("after the changes", violet) and **Today** ("current export", blue-gray); the selected one is filled with its color. `Expected` is selected when the page opens; without `CIDs_Expected.csv`, only `Today` exists. Each view shows its own structure as it is: nothing marks what changed or what is pending. The differences are spelled out in `Case_Message.txt`, and you report them to the user in the chat.
- **Tabs:** **Graph** and **Table**, as in the console. Both follow the view, the search, the service-line filter and the clicked CID.
- **Graph layout:** the root on top, centered, with its short name to the right of its glyph. Below it, one card per service line (a direct child of the root), left to right in name order (so the numbers `01`, `02`, ... set it), joined to the root through a bus. A card's header holds the service line: its short name, its number and its child count (additional children included, as Falcon counts them, with how many are additional). Its rows hold the line's tenants by primary parent, one below the other, the tenants with an additional parent first; a CID below a tenant is indented under it. Each tenant's link leaves the line's trunk on the left of the card. Tenant names show their tag in gray.
- **Marks, as in the Falcon legend:** parent CIDs (the root and the service lines) are an orange cluster of dots, tenants are cyan dots. A CID that is not `active` is a hollow gray dot with a gray name. Two badge columns at the right edge of each card hold the settings: **P** (purple) when Policy Inheritance is enabled, **D** (yellow) when Detection Aggregation is enabled; a disabled setting leaves its slot empty. The link to a CID with Policy Inheritance enabled is purple.
- **Additional parents:** the tenant's row gets a `+ <parent>` chip, and a dashed link runs from a port on top of the parent's card, along a channel under the bus and down the gutter left of the tenant's card, into the tenant's row.
- **Legend** (top-left, next to the toolbar; it starts hidden in windows narrower than 1500 px): counts of what is visible: all CIDs, parent CIDs, tenant CIDs, inactive CIDs (only when there are any), parent links, CIDs with Policy Inheritance enabled, CIDs with Detection Aggregation enabled, additional parents.
  - **Parent CIDs** expands into the service lines, each with its tenant count (by primary parent) and an eye that hides or shows it. Clicking a line's name shows only that line (click again to undo); **Show all service lines** resets. A tenant shows when its line or its additional parent's line is shown, and brings its parents up to the root; a line shown only for that keeps just its header, faded.
  - The eyes on Policy Inheritance, Detection Aggregation and Additional parent hide or show their badges and purple links, or the chips and dashed links.
- **Toolbar:** show/hide the legend, fit to screen, zoom in, zoom out. The mouse wheel zooms at the pointer; dragging pans. The view is framed to fit the visible CIDs (never past 115%) when the page opens and after every view or filter change and window resize, keeping clear of the legend.
- **Clicking a CID** (its dot, its name or its card header) lights up its whole chain (parents up to the root, both when it has two, and children down): the chain's links turn white (purple where Policy Inheritance is enabled) and everything else fades. It also opens the **details drawer** on the right: the name and what the CID is (`Root CID`, `Service line`, or `Tenant · <service line>`), the CID String with a **Copy** button (`To be created` for a `NEW-<n>`), status, endpoints (from the export) and child count, the parents (tagged Primary or Additional), the three settings (Policy Inheritance, Detection Aggregation, Incident Aggregation) and the children. Parents and children are clickable. The view moves just enough for the drawer not to cover the CID. Esc, the close button or a click on empty space closes it.
- **Table:** one row per visible CID in tree order, names indented by depth, until a column header is clicked to sort by it (click again to reverse, a third time to go back to tree order). Columns: CID name, type, service line, additional parent, status, endpoints, Policy Inheritance, Detection Aggregation, child CIDs and CID String (with a copy button). The bar above it repeats the service lines as toggle chips and counts the rows. Clicking a row opens the details drawer, and the table narrows to make room for it.
- **Source** (bottom-right of the graph): the CID export time (from `Input/CIDs.csv`) and the generation time.

### What the case message contains

`Output/<day>/Case_Message.txt` is written in English for CrowdStrike support and lists only what differs between Today and Expected:

1. **GENERAL NOTES:** identify CIDs by CID String; Incident Aggregation must always equal Detection Aggregation (only with `INCIDENT_FOLLOWS_DETECTION` on); names after the rename step are the new names; do the steps in order; do not change anything that is not listed.
2. **Steps**, numbered and included only when they have content, in this order:
   1. CREATE CIDs: name, parent, additional parent, settings.
   2. RENAME CIDs: `CID string: "current name" -> "new name"`.
   3. CHANGE PARENT LINKS: grouped into moves, removals and additions, each saying which parent(s) the CIDs must end up with.
   4. CHANGE SETTINGS: one list per setting and direction, all disables first, then enables.
   5. DELETE CIDs: with the current parent and the number of registered endpoints, and a request to tell us if anything is needed before deletion.
3. **INACTIVE CIDs:** for each inactive CID in the steps, a request to skip it if the console refuses and report it in the case.
4. **EXPECTED RESULT:** total CIDs, deleted CIDs, child count of every parent (counting additional-parent links, as Falcon does), additional parents, and the final state of each setting. Support uses this to check their work, and we use it to validate the next export.

CIDs are listed in tree order of the expected structure. The message opens with `Hello,` and closes with `Thanks,`. Add the support engineer's name or the user's signature only if the user asks. When nothing is pending, the script deletes any stale `Case_Message.txt`.
